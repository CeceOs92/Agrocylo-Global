# Incident Response Runbook

**Issue #780** — Emergency Response Procedures

This runbook describes detection, authorization, and response procedures for live production incidents affecting the Agrocylo contracts. It is meant to be followed by on-call operators in real time and should be drilled regularly.

## Quick Reference

| Role | Action | Who | Time |
|------|--------|-----|------|
| **Detect** | Monitor alerts, receive reports | Ops team, users | ~1 min |
| **Assess** | Verify incident, impact, scope | Ops lead | ~5 min |
| **Notify** | Page on-call guardian and governance committee | Incident commander | ~2 min |
| **Authorize Pause** | Guardian (2-of-3 signers) approves emergency pause | Guardian committee | ~5-10 min |
| **Pause** | Guardian calls `pause()` instantly | Guardian signer | ~1 min (no timelock) |
| **Investigate** | Root-cause analysis, prepare fix | Dev team | ~1-24 hours |
| **Propose Fix** | Governance proposes upgrade/parameter change | Governance member | ~1 hour |
| **Vote** | Governance committee votes (yes/no) | Governance voters | 7+ days (voting period) |
| **Queue** | If passed, queues for execution | Governance member | ~1 minute |
| **Wait** | Timelock delay (2 days for params, 14 days for upgrades) | N/A | 2-14 days |
| **Execute** | Execute proposal (calls `upgrade` or `migrate`) | Governance member | ~1 minute |
| **Verify** | Confirm fix is live and contracts operational | Ops team | ~15 min |
| **Unpause** | Governance calls `unpause()` once migration verified | Governance member | ~1 minute |

## 1. Detection

### Monitoring Alerts

The following conditions should trigger immediate investigation:

- **Fund Transfer Anomaly** — Large or unexpected transfer from escrow contract
- **Campaign Lifecycle Violation** — Campaign status transitions in wrong order (e.g., `Settled` → `Funding`)
- **Batch Refund Spike** — Sudden increase in refund requests (may indicate investor panic or malfunction)
- **Order Confirmation Timeout** — Orders stuck in `Pending` beyond expected window
- **Governance Quorum Drop** — Voting committee members go offline (loss of operational capacity)

### User Reports

Users may contact support via:
- Email: `ops@agrocylo.com` (on-call monitored)
- Slack: `#incidents` (on-call responds)
- Public status page: `status.agrocylo.com`

Triage any report mentioning:
- Loss of funds
- Stuck campaigns or orders
- Inability to withdraw investments
- Governance failures

### Initial Triage (Ops Lead)

1. **Reproduce** — Attempt to trigger the reported behavior
2. **Scope** — Determine which contracts are affected (escrow, registry, basket, governance)
3. **Severity** — Classify as:
   - **SEV1 (Critical)** — Funds actively at risk or lost; requires immediate pause
   - **SEV2 (High)** — Major functionality impaired; fix required within hours
   - **SEV3 (Medium)** — Minor functionality issue; can wait for next scheduled release
4. **Impact** — Quantify:
   - Number of affected users
   - Amount of funds at risk
   - Duration of outage so far

**If SEV1 or SEV2, proceed immediately to §2 (Authorization). For SEV3, follow normal governance flow.**

## 2. Authorization & Pause

### Who Can Pause?

- **Guardian multisig account** (2-of-3 committee) — can call `pause()` instantly
- **Governance contract** — can call `pause()` after normal proposal/voting/queuing (slower, not for emergencies)

For an emergency, **Guardian must authorize pause immediately**. This does not require governance approval (guardian is separate for this reason).

### Guardian Notification

Send authenticated, out-of-band notification to all 3 guardian signers with:

1. **Incident Summary** (1-2 sentences)
2. **Impact** (funds at risk, affected users)
3. **Requested Action** — "Approve emergency pause" or "Hold, investigating further"
4. **Verification Code** — A random code generated by ops and confirmed out-of-band
   - Example: `PAUSE-SEV1-20250915-A7F9D2`
   - Used to prevent accidental/spoofed pause requests

Example message:
```
INCIDENT ALERT: SEV1 - Escrow contract transferring funds without authorization
Impact: $50,000 USD equivalent at risk
Action: PAUSE (verify code PAUSE-SEV1-20250915-A7F9D2)
Contact: ops-lead@agrocylo.com / +1-555-INCIDENT
```

### Decision

Guardian committee (2-of-3) must reach consensus:
- **Approve pause** → Execute step 3 (Pause)
- **Investigate further** → Go back to step 1 (Detection); do not pause yet
- **Reject pause** → Document reason; escalate to governance if ongoing risk

**Timeframe:** Target decision within 5-10 minutes of notification.

### Pause Execution

Once 2-of-3 guardians approve:

```bash
# Guardian signer A
soroban contract invoke \
  --id C_PRODUCTION_ESCROW_ID \
  --source guardian-signer-a \
  -- pause \
  --caller GUARDIAN_MULTISIG_PUBKEY

# Guardians B and C must co-sign this transaction
# (soroban will prompt for signatures)
```

Repeat for each affected contract:
- `production_escrow`
- `registry`
- `investment_basket`
- **NOT governance** (governance must remain operational to un-pause)

**Output:** Each `pause()` call returns `Ok(())` and emits an event: `(symbol_short!("paused"), boolean_true)`.

**Expected state after pause:**
- All fund-moving operations fail with `Paused`
- All read-only views continue to work
- Exception: `registry::record_order_outcome` **is not pause-gated** (intentional; see CONTRACT_UPGRADES.md §3)

## 3. Investigation

### Dev Team Analysis

**Parallel to pause authorization**, development team begins investigating root cause:

1. **Examine logs** — Check contract event logs, RPC error responses
2. **Review recent changes** — Git commits, deployed code version
3. **Trace affected transactions** — Walk through each fund movement step-by-step
4. **Identify root cause** — Bug in contract logic, malicious input, external dependency failure, etc.

### Prepare Fix

Once root cause is identified, prepare one of:

- **Contract Upgrade** — If bug is in code
  - Requires governance vote, upgrade timelock (14 days)
  - Must be accompanied by storage `migrate` if schema changed

- **Parameter Change** — If configuration is wrong
  - Requires governance vote, shorter timelock (2 days)
  - Examples: adjust fee rate, update supported tokens, change dispute window

- **Governance Configuration** — If governance itself is broken
  - Requires careful coordination; escalate to community leadership

**Do not attempt to fix without governance approval.** The pause buys time for a proper fix, not a shortcut to deploy unvetted code.

## 4. Governance Proposal

### Draft Proposal

The governance contract's `propose` function requires:
- `target_contract` — Which contract to call (e.g., `C_PRODUCTION_ESCROW_ID`)
- `function_name` — Which function (e.g., `"upgrade"` or `"set_fee_config"`)
- `args` — Encoded arguments (contract-specific)

For upgrades, use `propose_upgrade` helper:
```bash
soroban contract invoke \
  --id C_GOVERNANCE_ID \
  --source proposer \
  -- propose_upgrade \
  --caller GOVERNANCE_PROPOSER \
  --new_wasm_hash WASM_HASH_OF_FIXED_BYTECODE
```

For other changes, use generic `propose`:
```bash
soroban contract invoke \
  --id C_GOVERNANCE_ID \
  --source proposer \
  -- propose \
  --caller GOVERNANCE_PROPOSER \
  --target_contract C_PRODUCTION_ESCROW_ID \
  --function_name "set_fee_config" \
  --args [C_FEE_COLLECTOR, 250]  # fee_collector, fee_rate_bps
```

### Announcement

Post proposal announcement to community channels:

```
🚨 GOVERNANCE PROPOSAL: Fix for recent ${INCIDENT}

Proposal ID: ${PROPOSAL_ID}
Target: ${CONTRACT_NAME}
Action: ${ACTION} (e.g., "Upgrade to v2.1.0")
Root Cause: ${BRIEF_DESCRIPTION}
Fix: ${WHAT_CHANGES}

Voting Period: ${START_BLOCK} to ${END_BLOCK} (7 days)
Status: OPEN - cast your vote now

Details: https://governance.agrocylo.com/proposal/${PROPOSAL_ID}
```

### Voting

Each governance committee member votes:

```bash
soroban contract invoke \
  --id C_GOVERNANCE_ID \
  --source voter \
  -- vote \
  --caller VOTER_ADDRESS \
  --proposal_id PROPOSAL_ID \
  --vote_yes true   # or false
```

**Quorum requirement:** Voting power >= configured quorum. Default: 50%.

### Queue (If Passed)

Once voting period ends, if proposal passed:

```bash
soroban contract invoke \
  --id C_GOVERNANCE_ID \
  --source queuer \
  -- queue \
  --caller GOVERNANCE_QUEUER \
  --proposal_id PROPOSAL_ID
```

This locks the proposal in and starts the timelock countdown.

### Timelock Wait

- **Parameter changes** — 2-day timelock (default)
- **Contract upgrades** — 14-day timelock (default)

During this time:
- Community can review the proposed change
- Anyone can raise concerns in governance forums
- No opportunity to change the proposal (governance is immutable once queued)

### Execute

After timelock expires:

```bash
soroban contract invoke \
  --id C_GOVERNANCE_ID \
  --source executor \
  -- execute \
  --caller GOVERNANCE_EXECUTOR \
  --proposal_id PROPOSAL_ID
```

If the proposal targets `production_escrow.upgrade`:
- The execute call will invoke `production_escrow.upgrade(new_wasm_hash)`
- This updates the WASM bytecode on-chain
- Contract behavior changes immediately

If the proposal includes a data-structure change, `migrate` must be called next:

```bash
soroban contract invoke \
  --id C_PRODUCTION_ESCROW_ID \
  --source executor \
  -- migrate \
  --caller GOVERNANCE_EXECUTOR \
  -- <migration-specific-args>
```

**The contract stays paused during upgrade and migrate.** Once migration completes and is verified (see below), governance calls `unpause`.

## 5. Recovery Verification

### Confirm Fix Is Live

1. **Check contract code version** (if upgrade)
   ```bash
   soroban contract data read \
     --id C_PRODUCTION_ESCROW_ID \
     --key "SchemaVersion" \
     --network mainnet
   ```

2. **Verify new behavior** — Reproduce the original incident; confirm it's fixed
   - If incident was "campaign stuck in Funding", try marking harvest; should now work
   - If incident was "bad fee rate", check `get_fee_config`; should return new value

3. **Check contract state** — Verify data is intact and migration succeeded (if applicable)
   ```bash
   soroban contract invoke --id C_PRODUCTION_ESCROW_ID -- get_campaign --campaign_id 1
   # Should return consistent campaign state
   ```

### Unpause

Once fix is verified operational and secure:

```bash
soroban contract invoke \
  --id C_PRODUCTION_ESCROW_ID \
  --source governance-executor \
  -- unpause \
  --caller GOVERNANCE_ADDRESS
```

Repeat for each paused contract:
- `production_escrow`
- `registry`
- `investment_basket`

**Note:** Only governance can unpause (guardian cannot unilaterally resume). This ensures recovery goes through the accountable governance channel.

### Communicate Recovery

Post to community channels:

```
✅ INCIDENT RESOLVED

Incident: ${INCIDENT_NAME}
Status: PAUSED → FIXED → OPERATIONAL
Duration: ${TOTAL_TIME}

What Happened: ${INCIDENT_SUMMARY}
Root Cause: ${ROOT_CAUSE}
Fix Applied: ${FIX_DESCRIPTION}
User Impact: ${IMPACT_SUMMARY}
Funds Status: ${ALL_FUNDS_SAFE | COMPENSATION_PROCESSING}

Next Steps:
- Contracts are now UNPAUSED and accepting operations
- All pending transactions are being processed
- Post-incident review: Thursday at 2pm UTC in #governance

Thank you for your patience.
```

## Pause-Gating Matrix

This documents which entry points are gated by `require_not_paused` and therefore blocked while paused:

### production_escrow (13 gated entry points)

| Entry Point | Gated? | Notes |
|-------------|--------|-------|
| `create_campaign` | ✓ YES | Farmers cannot start new campaigns while paused |
| `invest` | ✓ YES | Investors cannot fund campaigns while paused |
| `start_production` | ✓ YES | Production status advances blocked |
| `mark_harvest` | ✓ YES | Harvest claims blocked |
| `create_order` | ✓ YES | Order creation blocked |
| `confirm_order` | ✓ YES | Order confirmations blocked |
| `settle` | ✓ YES | Settlement blocked (investors cannot claim yet) |
| `claim_returns` | ✓ YES | Investor payouts blocked |
| `refund` | ✓ YES | Refunds blocked (investor funds remain in escrow) |
| `open_dispute` | ✓ YES | Dispute initiation blocked |
| `resolve_dispute` | ✓ YES | Dispute resolution blocked |
| `batch_refund_investors` | ✓ YES | Batch investor refunds blocked |
| `batch_refund_orders` | ✓ YES | Batch order refunds blocked |

**Note:** Governance (`set_governance_contract`, etc.), fee configuration, admin/guardian setters, and all read-only views are **NOT** paused.

### registry (2 gated entry points)

| Entry Point | Gated? | Notes |
|-------------|--------|-------|
| `register_farmer` | ✓ YES | No new farmers can register while paused |
| `register_campaign` | ✓ YES | Campaigns cannot be registered while paused |
| `record_order_outcome` | ✗ NO | **Intentionally not gated** — escrow calls this during `confirm_receipt`, and pausing registry shouldn't brick escrow |
| Other reads/governance | ✗ NO | All other operations (views, setters) proceed normally |

### investment_basket (4 gated entry points)

| Entry Point | Gated? | Notes |
|-------------|--------|-------|
| `deposit` | ✓ YES | Basket deposits blocked |
| `fund_basket` | ✓ YES | Basket funding blocked |
| `withdraw_basket` | ✓ YES | Basket withdrawals blocked |
| `claim_basket_returns` | ✓ YES | Basket return claims blocked |

### governance (0 gated entry points)

| Entry Point | Gated? | Notes |
|-------------|--------|-------|
| `propose`, `vote`, `queue`, `execute`, etc. | ✗ NO | **Never paused** — governance must remain operable to restore other contracts |
| `pause` (gov-initiated) | ✗ NO | Governance can always call pause |

## Drill Procedures

Regular drills ensure operators and governance committee can execute this runbook under pressure.

### Testnet Drill Schedule

- **Monthly** — Full pause/investigate/propose/vote/upgrade/unpause cycle
- **Weekly** (ops team only) — Quick pause/unpause on governance alone

### Running a Drill

1. **Announce** — Post in #incidents: "DRILL: Simulated SEV1, pause authorized by 2025-09-15 10:00 UTC"
2. **Simulate incident** — (Ops) Mark a campaign with unexpected status, or invoke a write operation as an unauthorized account
3. **Execute runbook** — (Guardian + Governance) Follow steps 2-5 in real time
4. **Record output** — Capture transaction hashes, timestamps, error messages
5. **Debrief** — Did operators know their role? Were thresholds correct? Did governance vote pass?

### Success Criteria

A drill is successful if:
- [ ] Guardian authorization obtained within 10 minutes
- [ ] Pause executed on all three contracts (production_escrow, registry, investment_basket)
- [ ] All fund-moving operations fail with `Paused` while paused
- [ ] Governance proposal drafted and queued
- [ ] Voting reached quorum
- [ ] Timelock countdown was verified
- [ ] Unpause executed successfully
- [ ] Normal operations resume (test campaign creation, investment, settlement flow)
